# Adaptive Pure Pursuit (APP) Planner

C++/ROS implementation of the **Adaptive Pure Pursuit (APP)** path planner proposed in:

> **B. Li, Y. Wang, S. Ma, X. Bian, H. Li, T. Zhang, X. Li, and Y. Zhang**,  
> “Adaptive Pure Pursuit: A Real-Time Path Planner Using Tracking Controllers to Plan Safe and Kinematically Feasible Paths,”  
> *IEEE Transactions on Intelligent Vehicles*, vol. 8, no. 9, pp. 4155–4168, 2023.  
> DOI: [10.1109/TIV.2023.3296435](https://doi.org/10.1109/TIV.2023.3296435)

**If you use this repository, its implementation, or the APP planning method in academic work, please cite the paper above.**

---

## Overview

Adaptive Pure Pursuit (APP) is a lightweight real-time path planner for autonomous vehicles operating in cluttered environments.

The central idea is different from conventional search-based or optimization-based path planning:

> **APP uses a tracking controller itself as a path generator.**

A virtual vehicle is simulated to track a guidance path, referred to in the implementation as the **carrot path**. Because the resulting path is generated through a vehicle tracking model, its geometry naturally follows the kinematic behavior of the vehicle.

If the generated path collides with obstacles, APP does not launch a high-dimensional optimization problem. Instead, it:

1. detects the conflicting portion of the generated path;
2. determines a suitable deformation direction;
3. locally modifies the carrot path;
4. simulates the tracking controller again; and
5. repeats this process until a collision-free path is obtained or the iteration limit is reached.

The resulting architecture is:

```text
Initial carrot / guidance path
             |
             v
   Virtual Pure-Pursuit Tracking
             |
             v
   Kinematically generated path
             |
             v
       Collision check
        /           \
      safe        collision
       |              |
       v              v
    output     locate conflict segments
                      |
                      v
              deform carrot path
                      |
                      +----------+
                                 |
                                 v
                       track again
```

The computational efficiency comes from avoiding a conventional high-dimensional path search or nonlinear trajectory optimization inside the APP refinement loop.

---

# Why Use a Tracking Controller for Planning?

Pure pursuit is normally viewed as a **path-tracking controller**:

```text
reference path
      ↓
pure pursuit
      ↓
steering command
      ↓
vehicle motion
```

APP reuses this mechanism for **path generation**:

```text
carrot path
      ↓
simulate pure-pursuit tracking
      ↓
virtual vehicle trajectory
      ↓
planned path
```

This has an important consequence.

The path is not generated as an arbitrary geometric curve and then checked afterwards for whether a vehicle can follow it. Instead, it is generated by propagating a vehicle model under steering commands.

In this C++ implementation, the simulated state evolves according to a kinematic bicycle model of the form

```text
x      <- x + v cos(theta) dt
y      <- y + v sin(theta) dt
theta  <- theta + v / L tan(delta) dt
```

where:

- `v` is the virtual vehicle velocity;
- `L` is the wheelbase; and
- `delta` is the steering angle generated by pure pursuit.

The implementation additionally limits:

- steering angle; and
- steering-angle rate.

Therefore, the generated path is consistent with the kinematic model and steering limits implemented in the virtual vehicle.

# C++ Implementation Architecture

The main planning pipeline of the ROS demonstration is:

```text
Built-in road / current environment
              |
              v
       DpPathDecider
              |
              v
    coarse carrot/reference path
              |
              v
         APP_Planner
              |
              v
     PurePursuitControl
              |
              v
    controller-generated path
              |
              v
        collision?
        /        \
      no          yes
      |            |
      v            v
   publish    local deformation
                  |
                  v
             track again
```

The implementation therefore contains two planning layers:

### 1. `DpPathDecider`

An engineering front-end used in this ROS demo to obtain a reasonable obstacle-aware guidance path.

### 2. `APP_Planner`

The core implementation of the Adaptive Pure Pursuit method described in the paper.

The APP planner can conceptually operate on any suitable carrot/reference path; it is not intrinsically tied to the DP front-end.

# Core APP Algorithm

The main implementation is located in:

```text
src/AppPlanner/planning/app_planner.cc
src/AppPlanner/planning/app_planner.h
```

The main interface is:

```cpp
bool APP_Planner::Plan(common::data::Trajectory& smooth_path);
```

Its logic is approximately:

```cpp
resample carrot path

while iteration < maximum iteration:
    simulate pure-pursuit tracking

    detect collision points

    if no collision:
        return success

    group collision points into local segments

    deform each conflicting carrot-path segment

    stitch modified segments back into global carrot path

    enlarge local refinement range

return failure
```

This iterative structure is the heart of APP.

---

## Step 1 — Resample the Carrot Path

The input carrot path is first resampled:

```cpp
Resample(carrot_path_gloabl_, resample_resolution_);
```

The default spatial resolution is:

```cpp
resample_resolution_ = 0.02;
```

Resampling gives the controller and collision-refinement stages a sufficiently dense and approximately uniform path representation.

Two overloads are provided:

```cpp
Resample(Trajectory&, double step);
Resample(Trajectory&, int N);
```

The first resamples according to spatial resolution, while the second generates a specified number of points.

---

# Step 2 — Generate a Path Through Pure Pursuit

The planner creates:

```cpp
PurePursuitControl pp_path(
    carrot_path_gloabl_,
    start_state_,
    goal_state_,
    smooth_path);
```

The constructor directly runs the virtual tracking process and fills:

```cpp
smooth_path
```

with the simulated vehicle trajectory.

This is an important design feature of the implementation:

> `PurePursuitControl` is not merely computing control commands for another planner. It is itself being used to generate the planned path.

---

# `PurePursuitControl`

The class implements the simulated closed-loop path generator.

Important default parameters include:

```cpp
wheel_base_            = 0.1445;
nominal_v_             = 0.1;
max_steer_angle_rate_  = 0.5;
max_steer_angle_       = 0.6;

DT                     = 0.1;
lookahead_distance_     = 0.18;
intergrate_n_           = 5;
```

These values correspond to the small experimental vehicle used by this archived implementation.

---

## `GetLookaheadIndex()`

```cpp
void PurePursuitControl::GetLookaheadIndex();
```

This function finds the current nearest point on the carrot path and then searches forward for the pure-pursuit lookahead point.

The default lookahead distance is:

```cpp
lookahead_distance_ = 0.18;
```

Rather than searching the complete path every time, the implementation searches in a local forward window beginning from the previously identified vehicle index.

---

## `Controller()`

```cpp
double PurePursuitControl::Controller();
```

Implements the conventional pure-pursuit steering relation.

For the selected lookahead point, the controller evaluates the heading error

```text
eta = direction_to_lookahead - vehicle_heading
```

and obtains the desired steering angle approximately from

```text
delta = atan(2 L sin(eta) / lookahead_distance)
```

where `L` is the wheelbase.

The actual path-generation process uses the enhanced routine described below.

---

## `ImprovedController()`

```cpp
void PurePursuitControl::ImprovedController(
    common::data::Trajectory& output_result);
```

This is one of the key functions in the C++ APP implementation.

A conventional pure-pursuit simulation could instantaneously apply a newly calculated steering angle. A real steering system cannot.

`ImprovedController()` therefore explicitly considers:

```text
maximum steering angle
maximum steering-angle rate
```

The controller interval is divided into several smaller integration steps:

```cpp
dt = DT / intergrate_n_;
```

and the steering angle is progressively changed toward the desired value while respecting:

```cpp
max_steer_angle_rate_
```

and:

```cpp
max_steer_angle_
```

The virtual vehicle state is propagated after each sub-step.

This produces a path that reflects steering actuation limits rather than an idealized instantaneous steering response.

---

## `UpdateVehicleState()`

```cpp
void PurePursuitControl::UpdateVehicleState(
    const double delta,
    const double dt,
    common::data::TrajectoryPoint& state);
```

Propagates the virtual vehicle using the implemented kinematic bicycle model.

The updated states include:

```text
x
y
theta
v
phi
```

where `phi` stores the applied steering angle.

This routine is the mechanism through which vehicle kinematics enter the APP-generated path.

---

# Step 3 — Collision Detection

After a path has been generated, APP calls:

```cpp
GetConflictingPointsId(smooth_path, conflict_id);
```

For every sampled state, the actual vehicle footprint is constructed:

```cpp
frame_.env()->vehicle.GenerateBox(...)
```

and tested against the environment.

The function:

```cpp
Environment::CheckCollision(...)
```

checks overlap with the static obstacle polygons and point-cloud boundaries stored in the environment.

If:

```cpp
conflict_id.empty()
```

the current controller-generated path is accepted immediately.

---

# Step 4 — Build Conflicting Segments

Individual colliding samples are not modified independently.

The planner calls:

```cpp
CreateConflictedSegements(...)
```

to expand the collision indices into continuous local regions.

The default initial buffers are:

```cpp
left_buffer_  = 0.5;
right_buffer_ = 0.5;
```

After each unsuccessful outer iteration, they are increased by:

```cpp
single_left_buffer_  = 0.2;
single_right_buffer_ = 0.2;
```

Thus, APP begins with relatively local modifications.

If these are insufficient, the affected region becomes progressively larger:

```text
small local deformation
          ↓
retry
          ↓
still colliding
          ↓
larger deformation region
          ↓
retry
```

This is one aspect of the **adaptive** behavior of APP.

---

# Step 5 — Determine the Deformation Direction

For each colliding point, the planner calls:

```cpp
GetDeformatedNor(...)
```

The vehicle footprint is conceptually divided into left and right portions.

APP checks which side encounters the obstacle.

If the right side conflicts, the carrot path is pushed toward the opposite lateral direction.

If the left side conflicts, it is pushed in the other direction.

Conceptually:

```text
             obstacle
                █
                █

      vehicle path
-----------→-----------

right side collision
        ↓
push guidance path left
        ↓
simulate controller again
```

The deformation is therefore tied to local collision geometry rather than being a random perturbation.

---

# Step 6 — Estimate Collision Severity

The function:

```cpp
double APP_Planner::MeasureCollisionRate(...)
```

samples a collection of small boxes along several parts of the vehicle footprint.

The implementation checks:

```text
left region
middle region
right region
```

and counts the number of collision samples.

This produces a lightweight local measure of how strongly the vehicle footprint intersects the environment.

APP uses the difference between collision conditions on the two sides to determine how far backward along the carrot path the deformation should be applied.

---

# Step 7 — Trace Back to the Carrot Path

The simulated path and the carrot path are not identical.

When a collision appears on the simulated vehicle trajectory, APP must determine **which earlier carrot-path point caused the controller to produce that motion**.

This is handled by:

```cpp
FindMatchCarrotPointId(...)
```

The function first finds the closest carrot-path point and then traces backward according to the calculated traceback distance.

That point is then moved slightly along the selected deformation normal:

```cpp
deformated_path[index].x += deform_cost_ * nor.x();
deformated_path[index].y += deform_cost_ * nor.y();
```

with the default deformation step:

```cpp
deform_cost_ = 0.02;
```

This is a particularly important idea in APP:

> A collision on the generated vehicle path is corrected by modifying the upstream guidance path responsible for producing that motion.

---

# Step 8 — Re-track the Deformed Path

After a local carrot-path segment has been modified, APP does **not** directly use that deformed geometric curve as the final path.

Instead, it creates another virtual pure-pursuit controller:

```cpp
PurePursuitControl pp_path(
    deformated_path,
    deformated_path.front(),
    deformated_path.back(),
    single_smooth_path);
```

The vehicle then tracks the modified carrot segment again.

The newly generated vehicle trajectory is collision checked again.

This local refinement can repeat up to:

```cpp
inner_iter_max_ = 20;
```

iterations.

This repeated controller simulation is what preserves the basic philosophy of APP throughout refinement:

```text
modify guidance
       ↓
simulate vehicle tracking
       ↓
check actual generated path
```

rather than simply modifying the final vehicle path geometrically.

---

# Step 9 — Stitch Local Deformations

Once a local segment succeeds, it is stitched back into the global carrot path through:

```cpp
StitchGolbalPath(...)
```

The entire pure-pursuit simulation is then repeated from the updated global carrot path.

In the current ROS demo, the APP planner is created with:

```cpp
APP_Planner(..., 10);
```

so the outer adaptive refinement is allowed up to 10 iterations.

---

# Why the Generated Path Is Kinematically Meaningful

A major reason for using tracking control as the path generator is that the generated path results from repeated simulation of:

```text
vehicle state
     +
steering controller
     +
kinematic bicycle model
```

rather than from arbitrary interpolation between geometric samples.

The current implementation explicitly considers:

- wheelbase;
- vehicle pose;
- steering angle;
- steering-angle rate;
- longitudinal motion; and
- finite-time numerical integration.

Accordingly, the output is kinematically consistent with the vehicle model implemented by the planner.

# Auxiliary DP Guidance Planner

The ROS demonstration also contains:

```text
planning/decider/dp_path_decider.cc
```

implemented by:

```cpp
DpPathDecider
```

This module should be understood as an **auxiliary guidance-path generator in the current C++ demonstration**, rather than the defining mechanism of APP itself.

It operates relative to a reference line and constructs a coarse obstacle-aware path using dynamic programming.

The state lattice contains longitudinal stations and seven lateral candidates.

The default lateral range is approximately:

```text
-0.4 m  ...  +0.4 m
```

and the important parameters include:

```cpp
s_resolution                = 0.05;
horizon                     = 12.0;
collision_check_resolution  = 0.02;

w_obstacle                  = 10000;
w_lateral                   = 10;
```

Obstacle overlap receives a very large cost, while another exponential term encourages candidates to stay farther away from obstacle centers.

The resulting DP path becomes the carrot/reference path subsequently processed by APP.

---

# `DpPathDecider::Plan()`

The main DP entry is:

```cpp
bool DpPathDecider::Plan(
    const DiscretizedTrajectory& reference_line,
    Pose start_pose,
    Pose goal_pose,
    double start_v,
    Trajectory& trajectory);
```

Its major operations are:

```text
project start/goal onto reference line
              ↓
construct longitudinal/lateral lattice
              ↓
evaluate transition costs
              ↓
perform collision checking
              ↓
dynamic programming
              ↓
trace back minimum-cost states
              ↓
resample coarse guidance path
```

The resulting path is then passed to APP for controller-based generation and local adaptive refinement.

## Replanning Logic

The node checks whether:

```text
current APP path collides with obstacles
```

or the vehicle has progressed sufficiently far along the previously published trajectory.

When replanning is required:

```cpp
ProcesByDP();
PublishInfoToAPP();
ProcessAPPRef();
```

are executed.

The practical pipeline is therefore:

```text
road reference
     ↓
DP guidance generation
     ↓
APP refinement
     ↓
trajectory construction
     ↓
ROS publication
```

# Important Functions in `node.cpp`

## `ProcesByDP()`

Generates a coarse obstacle-aware guidance path using `DpPathDecider`.

Converts the APP-generated path into a trajectory suitable for publication.

## `SendTrajectory()`


```cpp
sandbox_msgs::Trajectory
```
